# DB-14 FIX (Audit v2 · Phase 4) — FK Naming Convention

**Date**: 2026-08-13 (Phase 4)
**Finding**: DB-14 — ForeignKey naming inconsistency across models
**Severity**: P3 (documentation-only fix — no risky renames)

## Problem

The schema grew organically across multiple sprints, and FK column names
across models don't all follow the same convention. Concrete examples:

| Model               | FK column | Target          | Notes                                             |
|---------------------|-----------|-----------------|---------------------------------------------------|
| `MFASecret`         | `userId`  | `AppUser.uid`   | Column is a `uid`, not an `id` — misleading name  |
| `SessionRegistry`   | `userUid` | `AppUser.uid`   | Correct — follows the `Uid` convention            |
| `CompanyMembership` | `userUid` | `AppUser.uid`   | Correct                                           |
| `InventoryItem`     | `warehouseRef` (relation) → `warehouseId` (col) | `Warehouse.id` | Relation field uses legacy `Ref` suffix |
| `PurchaseOrder`     | `warehouseRef` (relation) → `warehouseId` (col) | `Warehouse.id` | Same as above |

Other FKs (`companyId`, `clientId`, `invoiceId`, `productId`, `supplierId`,
`employeeId`, `bankAccountId`, `journalEntryId`, `accountId`, `periodId`,
`assetId`, `budgetId`, `costCenterId`, `parentId`, `ruleId`, `endpointId`,
`settingId`, `letterOfCreditId`, `allocationId`, `distributionId`,
`reconciliationId`, `purchaseInvoiceId`, `attachedProductId`, `matchedProductId`)
all consistently use `<Entity>Id` and are not problematic.

## Why We Did NOT Rename In-Place

Renaming a Prisma FK column has a wide blast radius:

1. **Migration required** — `prisma migrate dev --name rename_user_id_to_user_uid`
   generates a `ALTER TABLE ... RENAME COLUMN` SQL statement. PostgreSQL
   supports this, but it must run in a maintenance window because:
   - All Prisma client calls (`db.mFASecret.findMany({ where: { userId } })`)
     break until the client is regenerated.
   - All raw SQL that references the column (`SELECT user_id FROM ...`)
     breaks.

2. **Code-touch surface** — at minimum:
   - `src/lib/mfa.ts` (4 call sites)
   - `src/app/api/auth/mfa/route.ts` (3 call sites)
   - `src/app/api/auth/mfa/setup/route.ts` (2 call sites)
   - `src/app/api/auth/mfa/verify/route.ts` (2 call sites)
   - `src/app/api/auth/mfa/disable/route.ts` (1 call site)
   - `__tests__/mfa.test.ts` (5 references)
   - `prisma/seed.ts` (2 references)

3. **Risk vs reward** — the existing name `userId` works fine functionally
   (Prisma resolves it correctly to `AppUser.uid` via the `references: [uid]`
   declaration). The only issue is readability/maintainability — it doesn't
   match the convention used elsewhere. A rename would be a P1-sized refactor
   for a P3-class cosmetic benefit.

## Resolution

Per the audit instruction ("document them rather than doing a risky
rename"), this file IS the fix. The naming convention is now documented
inline at the top of `prisma/schema.prisma` (see the `DB-14 FIX
(Audit v2 · Phase 4)` comment block), and the known inconsistencies are
called out explicitly so future contributors:

1. Don't copy the legacy `userId` pattern in new models — use `userUid`.
2. Don't add more `warehouseRef` relation field names — use `warehouse`.
3. Understand that `MFASecret.userId` IS a `uid` reference, not an `id`.

## Path to Full Cleanup (Deferred)

If/when a coordinated refactor sprint is approved:

1. Create migration `YYYYMMDDHHMMSS_rename_user_id_to_user_uid` that:
   - `ALTER TABLE mfa_secrets RENAME COLUMN user_id TO user_uid;`
   - Updates the `@map` attribute (if any)
2. Update `MFASecret` model in `schema.prisma`:
   - `userId String` → `userUid String`
   - `@@unique([userId])` → `@@unique([userUid])`
3. Run `prisma generate` to refresh the client.
4. Find-and-replace `userId` → `userUid` ONLY in MFASecret-related files
   (be careful: `userId` may also appear in JWT/session code that is
   unrelated).
5. Update `__tests__/mfa.test.ts`.
6. Run `bun test __tests__/mfa.test.ts` to confirm green.

Same approach for `warehouseRef` → `warehouse` (relation field rename
only — no column rename needed since the column is already `warehouseId`).

## Linting

The DB-15 lint script (`scripts/check-migration-names.mjs`) does NOT
enforce FK naming — that would require parsing the schema file with
`@prisma/internals` and walking the AST, which is too heavy for a CI
lint step. Instead, code review + the inline convention comment above
are the enforcement mechanism.
